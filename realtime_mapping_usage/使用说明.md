## 1. 找到的现成入口

`mid360-fastlio-ray-trace` 是本机最适合当前 Mid-360 的启动入口。

```text
真实 Mid-360 点云 + 内置 IMU
        ↓
FAST-LIO2 原生驱动与定位
        ├─ /lidar：传感器坐标点云，mid360_link
        ├─ /odometry：位姿
        └─ /tf：odom → mid360_link
                    ↓
            RayTracingVoxelMap
                    ├─ /global_map：全局体素点云
                    └─ /local_map：局部体素点云
                                ↓
                        Rerun / DimOS Viewer
```

CostMapper 是可额外拼入的模块：global_map/merged_map → global_costmap。默认光追蓝图未包含它。

实时结果是三维点云/体素地图。此前交付的 GLB/OBJ 三角网格另用了 `data/maps/reconstruction_20261014/raytrace_surface.py` 等后处理脚本；本蓝图没有自动连续生成这些表面模型。

## 3. 本机准备

Windows PowerShell 中进入 Ubuntu：

```powershell
wsl -d Ubuntu-22.04
```

后续代码都在 Ubuntu 中执行。按此前实际采集参数，雷达为 192.168.1.3，雷达网卡为 192.168.1.111；现场地址若变化，需要同步修改。

```bash
ip -br addr
ip route get 192.168.1.3
ping -c 4 192.168.1.3
```

先在旧任务窗口 Ctrl+C 停止旧建图/主动采集程序，关闭 Livox Viewer。不要另起第二个驱动争用雷达，也不要同时运行会重配置雷达的 `record_mid360_raw.py`。录制本次建图输入使用下面同一进程的 --record。

本机曾出现 LCM 接收缓冲区不足提示，可在开始前临时提高上限：

```bash
sudo sysctl -w net.core.rmem_max=33554432
sudo sysctl -w net.core.wmem_max=33554432
```

本次核查确认：现有 Python 环境、FAST-LIO2 原生程序和光追原生程序都在；启动帮助可正常运行，无需重新安装所有依赖。安装检查结果在 `installation_check.json`。

## 4. 最短启动方式

已准备本机专用脚本，运行时才会连接真实雷达：

```bash
bash '/mnt/d/未来机器人/realtime_mapping_usage/start_mid360_raytrace.sh'
```

它会切换到当前源码、激活现有环境、选用 LCM、设置已用的雷达地址、启用网页显示并录制 lidar/odometry/tf。若发现已有 FAST-LIO2，会退出并提示先停止旧实例。它不会自动修改网卡或内核参数。

## 5. 手动启动的完整等价命令

脚本与本节命令二选一，不要两套同时运行。

```bash
source /home/ll175/venvs/dimos-mapping/bin/activate
cd '/mnt/d/未来机器人/ku/dimos-main'
export PYTHONPATH="$PWD${PYTHONPATH:+:$PYTHONPATH}"
export DIMOS_TRANSPORT=lcm
export OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=2
unset DIMOS_MID360_PCAP

dimos --transport lcm --rerun-open web \
  --record sqlite --record-topics 'lidar,odometry,tf' \
  run mid360-fastlio-ray-trace \
  --lidar-ip 192.168.1.3 --host-ip 192.168.1.111 \
  --voxel-size 0.08 --filter-size-surf 0.08 --filter-size-map 0.1 \
  --dense-publish-en false --pointcloud-freq 10 --odom-freq 30 \
  --max-range 30 --emit-every 2 --global-emit-every 10
```

库内蓝图将地图体素覆盖为 0.05 米，这里显式改为此前使用的 0.08 米。`pointcloud-freq 10` 为前端点云目标频率；在实际约 10 Hz 输入时，emit_every=2 对应局部地图约 5 Hz，global_emit_every=10 对应全局地图约 1 Hz。这是发布配置，不是实测实时性能认证。

必须使用 LCM：当前 C++ FAST-LIO2 SDK 不支持直接使用全局默认 Zenoh。此前离线回放的光追阶段用过 Zenoh，不应将那一阶段的通信配置原样套到实时 FAST-LIO2。

## 6. 正确打开网页

当前本机原生 Viewer 曾因 WSL 图形能力不支持 R32Float 退出，因此使用 `--rerun-open web`，在 Windows 的 Edge/Chrome 打开：

```text
http://localhost:9878/?url=rerun%2Bhttp%3A%2F%2F127.0.0.1%3A9877%2Fproxy
```

也可打开 `http://localhost:9878`，按网页提示连接 `rerun+http://127.0.0.1:9877/proxy`。

| 端口 | 当前作用 |
|---|---|
| 9878 | 独立 Rerun 网页查看器 |
| 9877 | 实时会话 gRPC 数据服务，地址需带 /proxy |
| 7779 | DimOS 网页控制台 |
| 3030 | 自定义 Viewer 的 WebSocket 控制服务 |

源码问题：`dimos/web/templates/rerun_dashboard.html` 内嵌页硬编码为 9090，数据源硬编码为 9876；与当前 constants.py 定义的 9878/9877 不一致。因此直接打开 7779 可能看到内嵌画面空白；先用上面的独立查看器地址。本次未修改模板。

## 7. 如何判断建图成功

1. 出现 `fastlio2 device connected` 只表示雷达接入成功，还需确认地图持续更新。
2. 雷达静止约 10 秒，等待初始化；再缓慢移动。
3. 查看 `world/global_map`、`world/local_map`；`world/odometry` 与 TF 辅助检查位姿。
4. 当前光追蓝图在 visual_override 中隐藏 `world/lidar`；这层不显示不代表雷达没数据。检查当前扫描可先单独运行 `mid360-fastlio`，停掉后再启动光追蓝图。
5. 若刚启动只有少量 `No transform ...`，观察初始化后是否消失；持续出现说明点云未匹配到位姿，不能当作成功建图。检查 odometry/tf 是否持续、时间戳是否连续和通信是否丢包，不要先盲目放宽 TF 容差。
6. 窗口一直占用属于前台运行；Ctrl+C 才会结束本次会话并刷新录制。

如果显示卡顿，先将 global_emit_every 从 10 改为 20。它减少全局大地图的发布负载，不能替代对算法计算、CPU 和通信的检查。

## 8. 结束后数据在哪里

日志会显示实际录制路径，本机通常为：

```text
D:\未来机器人\ku\dimos-main\recordings\<本次run-id>\memory.db
```

结束后检查（将示例路径换为本次实际路径）：

```bash
dimos mem summary '/mnt/d/未来机器人/ku/dimos-main/recordings/<本次run-id>/memory.db'
```

应看到 lidar、odometry、tf 有数据和合理时长。这些是 FAST-LIO2 处理后的点云/位姿/TF，用于地图重建；它不等同于原始雷达 PCAP，也不包含完整原始 IMU 数据包。根据此前流程可以继续生成去顶图和 GLB/OBJ 模型。

不要把 `dimos map global` 自动等同于原生光追重建：它是录制数据的另一条地图重建工具链；`--export` 导出的是其 PGO 点云，不是自动导出光追 GLB。库另有 `dimos/mapping/ray_tracing/utils/raytrace_rrd.py` 可用录制数据库离线重建光追可视化，但它依赖对应 Python 扩展，不能因为原生 Rust 可执行程序存在就认定 Python 扩展也已安装。

## 9. 可选加入 CostMapper

基础光追链路稳定后，把完整启动命令的蓝图部分改为：

```bash
run mid360-fastlio-ray-trace cost-mapper
```

其他参数保留；它在同一套雷达驱动之后加入 global_costmap 输出。当前本机已验证这个组合的 --help 能解析。默认地形参数尚未针对底盘校准，该蓝图本身也没有接入底盘控制或导航执行器。
