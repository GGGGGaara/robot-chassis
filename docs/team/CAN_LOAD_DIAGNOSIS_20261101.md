# CAN 零速与可视化负载对照（2026-11-01）

## 现场状态

遥控模式与急停问题分别处理后，底盘报告 vehicle_state=0、control_mode=1、error_code=0。下面所有控制检查均使用编译驱动 `zero_only=true`，没有前进/转向脉冲，观测轮速均为零。

| 条件 | 测量时长 | ready=true / false | 全零运动帧 | 结果 |

| 原建图与可视化负载 | 30s | 1262 / 196 | 473 | 反馈超时及 ENOBUFS，失败 |
| 停止建图与可视化后的组件隔离 | 30s | 1496 / 0 | 516 | 该窗口通过，不能代替完整负载验收 |
| 限制可视化缓存后的组件带负载对照 | 30s | 1497 / 1 | 515 | 无发送错误；一次 motion_age=0.30114s，仍失败 |

原负载时 WSL 可用内存约 0.5GB；调整后观测到约 4.7GB。曾观察到 USB/IP 连接断开、can0 消失，重新转接后恢复；尾延迟与断开的根因尚未结案，不能只归因于内存，也不能宣称 CAN 稳定性已通过。

原始报告在本机 `tracer_navigation/results/ground_mode_20261101/` 与 `results/bounded_viewer_20261101/`，不进入公开 Git。带负载组件测试没有沿用 `check_connection_zero.sh` 的全套导航就绪入口；当时重定位仍需重新核对，因此不把组件结果写成整套导航验收。

## 已实现的资源限制

`start_fixed_map_relocalization.sh` 显式设置 RerunBridge 的显示历史缓存默认 512MB，可用 `TRACER_RERUN_MEMORY_MB` 指定 128..1024MB。显示刷新：雷达/局部模型 2Hz，全局/加载参考模型 0.5Hz，显示 TF 10Hz。

这些限制只作用于可视化订阅和历史缓存；不改变真实雷达/里程计频率、建图算法输入、每 10 帧发布全局模型或原模型记录/保存逻辑。旧显示历史可能被缓存淘汰，持久模型记录仍由独立录制模块负责。预检通过真实 BlueprintConfigParser 核验模块参数、缓存限额、显示频率，并保留地图哈希与匹配参数检查。

轮速反馈 0.3s、系统反馈 0.6s、速度门控及其他停车条件未放宽。当前不能执行行驶验收或自动签署 site acceptance。

## 接下来

在没有底盘驱动运行、车辆静止时，更换 USB-CAN 的电脑 USB 端口，优先直连；重新读取设备 BUSID、等待 can0 完成枚举，再准备接口并重复严格零速检查。设备断开不能通过自动重连后继续原运动任务；需停止、核对状态并重新使能。

仍失败时，进一步对照 USB 线缆/端口、主机 USB/IP 转接与原生 Linux 控制端。不要以禁用错误检查、放宽看门狗或清除急停锁定作为修复。Windows 日志提供了设备释放/连接异常记录，但尚未识别导致释放的具体来源。

官方诊断参考：[usbipd-win 故障排查](https://github.com/dorssel/usbipd-win/wiki/Troubleshooting)。仅在专门的非运动诊断中采集 USB 日志，不将可能包含设备数据的原始日志公开上传。
